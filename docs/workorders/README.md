# 施工单

本目录记录 UAPA 按 Sprint 拆分的施工单：每个 Sprint 一份总览与若干张施工单。要实现的功能、
验收标准与依赖以[功能清单](../feature-list/README.md)为准；本目录回答按什么顺序施工、每步如何
验证。做完了没有、证据是什么，记在[验收目录](../acceptance/README.md)。

## 目录结构

```text
docs/workorders/
├── README.md                  本文
├── M1-00-<sprint-slug>.md     Sprint 总览
└── M1-01-<slug>.md …          施工单
```

对应的验收文件在 [`../acceptance/`](../acceptance/)，一单一份、与施工单同名；总览对应那边的
Sprint 收口文件（同名，全部工单完成后建立）。

## 编号与命名

| 对象 | 规则 | 例 |
|---|---|---|
| Sprint 号 | `M` 加正整数，不补零 | `M1`、`M12` |
| 工单号 | `<Sprint 号>-<两位序号>`；`00` 固定给总览 | `M1-00`、`M1-04` |
| slug | 英文 kebab-case，3～60 字符，只含 `a-z0-9-`；描述交付什么，不描述怎么做 | `agy-target` |
| 总览文件 | `M<n>-00-<sprint-slug>.md`；sprint-slug 是整个 Sprint 的主题 | `M1-00-v0-1-0-three-host-build.md` |
| 施工单文件 | `M<n>-<NN>-<slug>.md` | `M1-04-agy-target.md` |
| 一级标题 | 总览 `# Sprint 总览 M1-00：<主题>`；施工单 `# 施工单 M1-04：<名称>` | 编号与文件名一致 |

- 中文名称只写在一级标题中，文件名不用中文、不加日期。
- 编号一经分配不复用、不重排；作废的工单在总览表中标「已废弃」，文件保留。
- Sprint 号 `M<n>` 与功能清单的里程碑 M1～M6 是两套编号。提到里程碑时写「里程碑 Mx」。

## 总览「工单构成」表是权威源

一个 Sprint 声明覆盖哪些功能、哪张单依赖哪张单，只看总览的「工单构成」表。前三列的列序固定：
工单、名称、覆盖功能编号。施工单表头的「覆盖功能点」「依赖工单」与验收 §2 的功能清单是它的
副本，不一致时以总览为准。功能编号取自功能清单的模块文件，不另行编号。

## 拆单

- 按能否独立提交来切：一张单是一次可验证的交付，对应一个实现提交，典型 3～7 张。超过 7 张时
  在总览「目标与已定决策」中写明理由。
- 拆完能说明顺序依据：前一张的产出是后一张的输入，或写明可以并行。
- 「现状（已定位）」写真实的文件路径、函数名与计数，并分清已有且够用、已有但不对、完全没有。
- 「关键落地约束」写实施前必须核实的宿主行为与工具链假设、验证方式与得不出结论时的处理。
  宿主行为没有实测结论时，不按推测实现。
- 「不改的地方（红线）」写具体：哪个测试或夹具必须持续通过、哪条接口语义不动、哪个模块禁止
  扩展。

## 硬约束

每张施工单的「硬约束核对」逐行判断是否触碰以下约束，一行不删；填「是」的行写明验证方式，
验收 §1 把这些行带成判定条目。

| 硬约束 | 依据 |
|---|---|
| 守卫不静默失效：`requires` 中的能力目标不具备时该目标构建失败；守卫出错或宿主输入无法解析时，执行前与提示提交前检查拒绝 | P-01、P-04；F-03-13、F-04-03、F-04-04 |
| 产物零依赖：子进程入口只导入 `node:` 内置模块，hooks 模块只导入 `'claude-code'`；不附带 UAPA 运行时 | TA-01；[架构 §1](../architecture/architecture.md#1-组成与模块) |
| 不在运行时推断宿主：入口只按打包时注入的目标数据工作 | TA-05；[架构 §1](../architecture/architecture.md#1-组成与模块) |
| 确定性输出：产物与构建报告不含时间、绝对路径与用户名；同一输入逐字节相同 | TA-06 |
| 不越权写入：只写各插件目录、`<outDir>/uapa-report.json` 与配置 `marketplace` 时的 marketplace 文件（v0.4.0）；`--check` 不写文件 | TA-07、TA-08；SD-14、SD-41 |
| 安装不运行脚本：`package.json` 没有生命周期脚本；生产依赖只有 rolldown、yaml、zod | TA-10；F-10-03 |
| 能力数据有出处：只写已核实的宿主行为，注明宿主版本、核对日期与出处；未实测的能力记为不支持 | P-03；TA-09、TA-15 |

依据中的 P-NN 见[角色审计](../feature-list/stories.md#角色审计)，TA-NN 见
[技术验收](../feature-list/technical-acceptance.md)，SD-NN 见[范围决策](../feature-list/scope-decisions.md)。

## 施工流程

1. 按总览的顺序取一张工单，先核对「关键落地约束」；约束得不出结论时停在该步并报告。
2. 实施，运行工单「验收」节的命令。
3. 提交实现：Conventional Commits 前缀（`feat`、`fix`、`docs`、`test`、`chore` 等），正文用中文
   写明改了什么与理由。
4. 填写验收文件，把实现提交的哈希写入表头，单独提交，不修改上一个提交。
5. 验收结论为「通过」后推送 `main`。发布 tag 另需维护者确认。

施工单中不记 commit 号与验收结论，这两项只记在验收文件表头。
