# 验收记录

本目录记录每张施工单做完了没有、证据是什么、欠了什么。功能清单说明要实现哪些功能，
[施工单](../workorders/README.md)说明怎么施工，本目录记录结论与可复跑的证据。

一张施工单一份验收文件，与施工单同名，工单做完当场填写。全部工单做完后建立 Sprint 收口文件
（与总览同名），逐条核对总览的「Sprint 完成判定」。

## 目录结构

```text
docs/acceptance/
├── README.md                  本文：判准与索引
├── tech-debt.md               不属于任何 Sprint 的技术债（TD-NN）
├── M1-00-<sprint-slug>.md     Sprint 收口（与总览同名）
└── M1-01-<slug>.md …          一单一份，与施工单同名
```

一级标题：施工单的验收写 `# 验收 M1-04：<工单名称>`；Sprint 收口写
`# Sprint 收口 M1-00：<主题>`。编号与文件名一致。

## 什么时候才能标 ✅

1. 构建出产物并实际运行过一次才能标 ✅：夹具在临时目录中构建并比对，入口以 `process.execPath`
   运行；涉及宿主行为的条目以宿主实测为证据。单元测试全绿只是必要条件。
2. 只交付了一部分就写限定语（如“仅能力数据完成”），结论封顶为「有条件通过」。宁可低报，
   不可虚报：虚报会被后续工单当作既有能力依赖。
3. 工单的 ✅ 不能顶替功能点的逐条验收。§1 是工单维度、§2 是功能点维度，§2 的功能集合与总览
   「工单构成」表中该工单的覆盖功能一致。
4. 填不出证据就标 ⏳。「实际」列写测到的数量与输出（如“42 pass / 0 fail”“stdout 与期望逐字
   一致”），不写“符合预期”。

## 状态与结论

| 对象 | 取值 |
|---|---|
| 行级状态（§1、§2、§3） | ✅ 通过（证据非空） / ⚠️ 部分（写限定语，证据非空） / ⏳ 待执行 / ❌ 不通过 |
| 验收结论（表头） | 通过（§1、§2 全部 ✅，commit 号已回填） / 有条件通过（<条件>，§7 有去向） / 不通过 / 待定 |
| commit（表头） | 实现提交的 7～40 位哈希；回填单独一个提交，不修改实现提交 |
| 日期 | `YYYY-MM-DD` |

欠一条就是有条件通过，不是通过；括号里写明欠的是什么。

## 判断范围

表头「判断范围」说明证据来自哪里，只取以下值：

| 取值 | 何时用 | 对外表述 |
|---|---|---|
| 夹具与单元测试 | 证据来自单元测试、夹具比对与以 `process.execPath` 运行的入口用例 | 产物与入口在用例输入下成立，不转述为“已在宿主中验证” |
| 宿主实测 | 证据来自在宿主中加载产物或记录插件的运行结果 | 写明宿主版本，引用调研文档的实测小节 |
| 夹具与单元测试 + 宿主实测 | 两类证据都有 | 逐行在「证据」中注明“（宿主实测）” |
| 不涉及宿主行为判断 | 本单只涉及工具链、包结构或文档 | — |
| 待定 | 骨架初始值 | 结论已下时不得保留 |

## 一票否决

验收 §0 固定四行，任一项为「是」时该工单判「不通过」，不得记为技术债，也不得以「有条件
通过」放行。先处置缺陷，再在同一份验收文件中重新判定。填「否」也要给证据（用例名、夹具、
扫描命令或实测记录）。

| # | 一票否决项 |
|---|---|
| V1 | 守卫在能力缺失、守卫出错或输入无法解析时放行执行前检查，且构建报告未写明 |
| V2 | 插件产物导入 npm 包或依赖 UAPA 运行时 |
| V3 | 构建写入插件目录与构建报告之外的文件，或 `--check` 写入文件 |
| V4 | 能力数据含无出处的宿主行为 |

## 技术债与架构回填

- §6「技术决策」是架构文档的回填检查点：Sprint 中定下、而[架构文档](../architecture/architecture.md)
  或接口文档还写着“待定”“未核实”的，登记回填状态。
- §7「已知限制与技术债」每条写明去向（哪个功能、工单或 Sprint 接手），没有去向的不入账。
  不属于任何 Sprint 的改动（依赖升级、阻塞解除）记入 [`tech-debt.md`](tech-debt.md)。
